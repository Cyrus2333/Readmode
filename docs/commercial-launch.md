# Readmode 商业化落地计划

## 推荐形态

```text
Chrome Web Store 免费分发
        +
静态官网 / 隐私政策 / 帮助文档
        +
第三方支付页面
        +
人工或平台邮件发送离线签名许可证
```

Readmode 插件运行时不依赖自建后端，不上传文档，不要求账号，不做在线 license check。

## 阶段 0：当前预发布版

目标：完成产品验证，不收真实款。

- 基础 Markdown / HTML 阅读功能稳定；
- HTML 安全预览与原始运行边界清楚；
- 设置页有真实的 Pro 功能开关；
- 离线签名许可证可在本地验证；
- 生成 ZIP、运行检查和手工验收；
- 官网、隐私政策、条款、帮助页面已准备，但联系方式和商店链接仍待配置。

## 阶段 1：免费公开版

目标：验证留存和重复使用场景。

需要准备：

- Chrome Web Store 开发者账号；
- 正式产品名、图标、截图；
- 支持邮箱或公开 issue tracker；
- 公开隐私政策 URL；
- 真实的 Chrome Web Store 链接；
- 5–10 位 beta 用户和不含敏感信息的样例文件。

观察指标：

- 安装后首次成功预览率；
- Markdown / HTML 使用比例；
- 本地文件失败率；
- 7 日内重复打开率；
- HTML 原始运行模式使用率；
- 用户主动请求的 Pro 场景。

## 阶段 2：小范围付费验证

不要先开发完整订单系统。选择一个支持外部结账和邮件交付的支付平台，先用人工流程验证：

1. 用户点击官网或插件中的升级入口；
2. 第三方支付平台收款并发送订单通知；
3. 产品负责人核对订单；
4. 用离线签发脚本生成许可证；
5. 通过平台邮件或人工邮件发送；
6. 记录订单号、许可证 ID 和退款状态，但不记录文档内容。

只有当订单量和退款/客服异常足以证明自动化有价值时，才考虑 serverless 发码接口或支付 Webhook。

## 阶段 3：自动化（可选）

自动化会引入外部服务依赖，但不必把文档阅读变成 SaaS。可选组件：

- 支付平台 checkout；
- 支付平台邮件或交易通知；
- 极小的 serverless license delivery endpoint；
- 静态网站上的价格和购买页。

这一步不是首发条件，也不是当前实现范围。

## 不建议的方向

- 订阅制优先于一次性授权；
- 自建账号、文档云盘和团队协作空间；
- 每次打开文档都请求授权服务器；
- 让支付平台接触用户文档内容；
- 在前端保存支付或签发私钥；
- 为了防破解而收集设备指纹。

## 当前待负责人确认

- 正式品牌名和域名；
- 支持邮箱或仓库地址；
- 首个支付平台、货币和销售地区；
- 首个公开 Pro 价格；
- 退款期限和离线许可证的退款处理规则；
- 生产许可证密钥的保管人。
